# `results/comparison/`

Cross-arm tables that no single runner produces — they join rows from `results/greedy_baseline/`, `results/stable_ac/cov/`, and `results/heuristic_search/` (all built for other purposes) into one comparison, plus a set of diagnostics asking *why* the tuned heuristic ordering and change-of-variables help where they do. The top-level [`results/README.md`](../README.md) has the summary paragraphs for the headline tables; this file covers everything under here, including the smaller feature-sweep families it doesn't mention.

**Two caveats that apply across most of this directory:**

- **Budgets and caps are not uniform.** `GREEDY_VS_BESTCOV.md` compares greedy at 1,000,000 against best CoV at ≤20,000; `THREE_WAY_COST.md` matches all three arms at budget 10,000 and cap 24; the `*_B1K.md` feature sweeps run at budget 1,000 on CoV-transformed starts. Only arms drawn from the same matched block are directly comparable — check each table's own budget/cap row before comparing across files.
- **An unsolved row in a budget-capped block is `nodes = budget` with a blank path.** The `*_B1K.md` sweeps do not all solve 60/60 (`b1k_greedy` solves 29/60, for instance); every mean/median in those tables is stated as being over *solved rows only* for exactly this reason — a mean over the whole 60 would be dragged by the ceiling value, not the search.

## The headline three: `THREE_WAY_COST.md`, `GREEDY_VS_BESTCOV.md`, `nodes_comparison_subset60.csv`

These are the only tables in this directory that run all three techniques (or a subset of them) at the same node budget and cap, and they are not the same comparison — read the write-up before quoting a number:

- [`THREE_WAY_COST.md`](THREE_WAY_COST.md) is the matched one: greedy, best CoV, and the tuned heuristic ordering (`RECOMMENDED` in `experiments/heuristic_search/core/hsolve.py`) all at budget 10,000 / cap 24, gated on the length-only control reproducing the greedy column pop for pop.
- [`GREEDY_VS_BESTCOV.md`](GREEDY_VS_BESTCOV.md) is deliberately unmatched — greedy gets its full production budget (1,000,000) while best CoV is priced as an oracle over ≤20,000-node searches per candidate start — and says so explicitly, including that best CoV's own *finding* cost (6,177 + 909 searches) is a separate, much larger number from the 60 headline rows.
- `nodes_comparison_subset60.csv` is the widest join (six arms, three different budgets: 1M / 100k / 10k+20k) and is what the other two are partly built from; its trailing rows are aggregates, not presentations, so filter on a numeric `pres_id` before computing anything over it.

## The `*_B1K.md` family

Six single- or few-feature priority sweeps (`BMAX`, `S`, `MK`, `KDEN`, `K_VS_KDEN`, `KMS_EQUAL`) plus the CoV-selection variant (`COV_HEUR_SELECT_B1K.md`) all share one input, `cov_heur_b1k_subset60.csv`, and one pair of reference arms quoted in every one of their tables: `b1k_greedy` (length-only, 29/60) and `b1k_heur` (the full RECOMMENDED weight vector, 43/60). They exist to answer *which* piece of RECOMMENDED is doing the work — none of the single-feature or two-feature variants tested here beats the full RECOMMENDED ordering; read each file's own table for where it lands between the two reference arms.

## The `COV_*_FEATURE_DELTA` / `COV_KNOT_DENSITY` family

Three no-search diagnostics that ask whether the oracle best-CoV transform happens to move a presentation's RECOMMENDED features in the direction the heuristic already prefers — i.e. whether CoV and the tuned heap ordering are two views of the same effect, rather than independent techniques. `COV_FEATURE_DELTA.md` is the full 60-row version; `COV_AUTMIN_FEATURE_DELTA.md` restricts to the 17 rows where CoV genuinely left the Aut-orbit (not just relabelled it) and re-scores on Whitehead-minimal representatives; `COV_KNOT_DENSITY.md` redoes the knot-count comparison length-normalised, since a CoV that simply lengthens a relator can look worse on raw knot count while being no denser.
