**Two traps this carries a test for.** Filtering the benchmark out of the training file stops the shipped prefix walk at index 0, silently collapsing the 634-row pin to 0 in *both* arms; and the two arms share a dataset, a seed and an output directory, so a tag that did not carry the reward variant would have them resuming from each other's checkpoint.

**From the independent review**, two real changes to `heldout.py`: `build()` now compares the existing file's CONTENT rather than its row count, because a stale file of the same length would have survived as "already built" while the returned counts stayed correct — wrong only in the file a training run actually reads; and both prefix walks now reuse the lists already in memory (`ms_prefix_length(..., rows=)`), since the old log line re-`literal_eval`ed the whole 156k-row file just to print the "was" number, eagerly, even when `log` was a no-op. **And the content check turned out to be dead code where it mattered.** `run_ppo._ensure_dataset` returned early on `os.path.exists`, so `build()`'s comparison never ran for the file a training run actually reads — the guarantee held only in the tests that called `build()` directly. Found the hard way: a mutation run left `data/AC19_extended_ho60.txt` corrupted at the right row count and the next full suite consumed it happily. The existence short-circuit is gone (both builders are idempotent and now compare content, so calling them is a no-op when the file is right, at the cost of one source parse per process start — against an 8-hour run), `build_benchmark_dataset` got the same row-count-to-content fix, and the test that corrupts a file now uses a stem of its own with a `finally` repair, so a dying process can no longer poison the shared data file.

## 05:12:00 UTC · `91c74c0b`

**Hotfix: GPU resume crashed.** `PPOTrainer.load_state_dict` passed two of its three RNG states to `set_state` unconverted, and `run_ppo` resumes with `torch.load(..., map_location=device)` — which maps *every* tensor in the blob, RNG states included. On a GPU they arrive on CUDA and `set_state` raises `TypeError: RNG state must be a torch.ByteTensor`. Caught by the mandatory smoke run on the control arm, on its second execution, which is the first time the resume path ran.

**Changed:** [`experiments/ppo/ppo.py`](../experiments/ppo/ppo.py) — new `_cpu_rng` helper, routed through all three call sites so the asymmetry that caused this cannot come back; [`tests/ppo/test_policy_and_ppo.py`](../tests/ppo/test_policy_and_ppo.py) — a `_OffCpuTensor` stand-in makes the GPU-only failure reachable on a CPU-only machine, and the test also requires the resumed generators to continue the *same* stream, not merely to be accepted.

**Why it escaped.** The existing round-trip test loads with `map_location="cpu"` while production loads with `map_location=device`, so the test exercised a path production never takes. A resume test that resumes differently from the real resume is not a resume test. Both reverts reproduce the exact `TypeError` under mutation.

**Why the config generator exists.** `run_ppo.py`'s `__main__` defaults are not the notebook's: `BEAM_WIDTH` 8 against 1024, `BEAM_MAX_STEPS` 100 against 150, `EVAL_DATASET` `1190MS` against `benchmark60`, `USE_WANDB` off, a different `OUT_DIR`. Those defaults are right for a harmless laptop invocation and wrong for an arm — a headless run under them produces a number that looks like the experiment and is not it. `arm_config` executes the notebook's CONFIG cell and applies exactly the merge the RUN cell applies, so the two paths cannot drift. Verified end to end on CPU: the CLI built the held-out dataset (156,762 -> 156,708, 580 pinned), applied `Phi = -0.2 * (1L + 0K + 2MK + 20S)`, and wrote both checkpoint and jsonl under the expected tag `ppo-drt-AC19_extended_ho60-s20mk2-lam0.2-s142`.

**The GPU finding.** The offered GB10 boxes are the wrong part for this job. The workload is bandwidth- and launch-bound — 137,765 parameters, ~335 optimiser micro-steps per update at `MICRO_BATCH` 2048 — so VRAM is free headroom and bandwidth is the number that matters. GB10 lists at **116.7 / 120.5 GB/s measured** (273 GB/s raw) against an A100's ~1,555; its 119 GB of unified LPDDR5X is a capacity play this run cannot use, and it is `aarch64`. RTX 4090/5090 are a good fit on bandwidth and clocks. The load-bearing constraint is not the model though: **both arms must run on the same hardware**, since at one seed a GPU-architecture change between arms sits directly on top of the effect being measured — so the runbook leads with renting one 2-GPU box and running both arms on it, which makes the Colab control a free replicate.
