# [2026-07-24] A gap-vs-budget metric reads "turned over" exactly when the treatment wins hardest — check the TREATMENT's headroom, not just the control's [TRAP]

The scale test for the tuned heap ordering (EXP-28: both arms, 66 rows, budget 100,000 on Colab) pre-registered one decision metric: the solve-count gap over the baseline at each checkpoint, verdict "still widening / flat / turned over". The runner printed **turned over** — +14 at budget 1,000 shrinking to +6 at 100,000 — which by the pre-commitment meant "the ordering buys earliness, not reach; downgrade the recommendation".

The row level says the opposite. The tuned arm **finished the benchmark at 62,534 nodes — 60/60 graded rows solved** (its only misses were the six open reach problems). From there to 100,000 the treatment had zero headroom, so the gap could do nothing but compress while the baseline caught up on rows the treatment had long finished; the baseline meanwhile still scored **0/6 on bin 9**, rows the tuned arm solved 6/6 with a 3.4×–23× node multiplier against the baseline's own 1M-node data. The metric's "turned over" was produced *by the win*, not despite it.

This is the mirror image of [control-with-no-dynamic-range](control-with-no-dynamic-range.md), and the repo now has both failure directions on record: there, a null read as evidence because the **control** could not move at the tested budget; here, a win read as a loss because the **treatment** ran out of things to solve mid-run. Same root cause — a comparison metric is only meaningful on the range where *both* arms can still change.

**Rule:** before reading any trend verdict off a gap/Δ metric, check both arms' headroom at every point of the range: the number of rows each arm could still gain. The moment either arm saturates (treatment solves everything solvable, or control is structurally stuck), truncate the metric there and switch to row-level analysis — set differences (who solves what the other cannot), per-row node multipliers against reference data — for everything beyond. And when pre-registering such a metric, pre-register the saturation check with it.
